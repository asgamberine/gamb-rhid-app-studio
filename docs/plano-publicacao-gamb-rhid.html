Primeira informação necessária: onde o site principal está hospedado

DNS não consegue encaminhar somente o caminho /gamb-rhid. Para preservar o restante de gamberine.com.br, precisaremos configurar o servidor web atual ou uma rota Cloudflare específica para esse caminho. Sem essa informação, o deploy final não pode ser automatizado com segurança.

As categorias se sobrepõem: uma informação pode depender também de uma ação manual. Por isso, os totais dos filtros não devem ser somados.

Informações que você precisa disponibilizar

Preencha ou confirme estes itens. Segredos devem ser cadastrados diretamente no GitHub Environment, Cloudflare ou servidor, nunca incluídos neste HTML, em commits, issues ou mensagens.

01

Hospedagem atual de gamberine.com.br

Preciso informar Manual

Informar onde o site raiz está hospedado e quem administra o ambiente.

  • Provedor, painel utilizado e sistema operacional.
  • Servidor web atual: Nginx, Apache, cPanel, WordPress ou outro.
  • Se existe SSH, Docker e permissão para configurar proxy reverso.
  • Se o site raiz pode ser alterado ou deve permanecer intocado.

Modelo de hospedagem escolhido para o backend

Preciso informar Decisão

Confirmar se o container será executado no servidor atual, em uma nova VPS Linux ou em um provedor gerenciado que aceite Node, volume persistente e Docker.

Acesso administrativo ao servidor

Preciso informar Sensível

Disponibilizar host, porta, usuário de deploy e método de autenticação. Preferir chave SSH exclusiva, sem senha e sem acesso root direto.

  • A chave privada deve entrar somente no cofre de deploy.
  • O usuário precisa acessar Docker e apenas os diretórios da aplicação.

Acesso Cloudflare da zona gamberine.com.br

Preciso informar Sensível

Confirmar o Account ID, o Zone ID e gerar um API Token restrito às funções realmente utilizadas.

  • Workers Scripts e Workers Routes, se usarmos proxy por caminho.
  • Cloudflare Tunnel, se o servidor não receber conexões públicas.
  • Access Applications e Policies, se o acesso for privado.
  • DNS Edit apenas se precisarmos criar um hostname de origem.

Plano e permissões do GitHub

Preciso informar Decisão

Confirmar se o repositório continuará privado e qual plano será adotado. GitHub Pro ou Team é necessário para branch protection e environments em repositório privado. Aprovação obrigatória nativa de deploy privado pode exigir plano superior; sem isso, usaremos uma promoção explícita por tag.

Política de acesso ao aplicativo

Preciso informar

Escolher entre acesso público com login RHiD ou acesso restrito antes do login. Para uso pessoal ou interno, a recomendação é Cloudflare Access.

  • Lista de e-mails ou domínio autorizados.
  • Método: código por e-mail, Google, Microsoft ou outro IdP.
  • Duração máxima da sessão de acesso externo.

Ambientes desejados

Preciso informar

Confirmar produção e homologação. Sugestão: produção no caminho final e homologação protegida em staging.gamberine.com.br/gamb-rhid ou hostname equivalente.

Armazenamento e destino dos backups

Preciso informar Sensível

Informar volume persistente disponível e um destino externo criptografado: S3 compatível, Cloudflare R2, Backblaze B2 ou outro.

  • Retenção diária, semanal e mensal desejada.
  • Região de armazenamento e responsável pela restauração.
  • Credenciais somente no cofre do ambiente.

Regra para habilitar marcações oficiais

Preciso informar Aprovação

Definir quem pode alterar ALLOW_OFFICIAL_RHID_PUNCH para true, em qual data e após quais testes. Homologação deve permanecer sempre em false.

Conta RHiD para homologação funcional

Preciso informar Não armazenar

Indicar uma conta autorizada para validação manual de login e consultas. A senha não será salva em GitHub Secrets nem usada em testes automáticos. Testes automatizados utilizarão respostas simuladas.

Retenção e privacidade

Preciso informar Legal

Definir por quanto tempo manter horários, histórico e localização, além do responsável por solicitações de privacidade e incidentes.

Contatos de monitoramento e incidente

Preciso informar

Informar e-mail, canal de alerta e responsável principal e substituto para indisponibilidade, falha de backup, erro de deploy e eventos de segurança.

Objetivos operacionais

Preciso informar

Confirmar disponibilidade esperada, janela de manutenção, RPO máximo de perda de dados e RTO máximo para restauração. Sugestão inicial: RPO de 15 minutos e RTO de 30 minutos.

Decisão de roteamento para o caminho final

As duas opções preservam o site principal. A escolha depende da resposta sobre a hospedagem atual.

02
Preferencial

Proxy reverso no servidor atual

O Nginx ou Apache de gamberine.com.br encaminha somente /gamb-rhid/ para o container Node.

  • Menos camadas e menor custo operacional.
  • Mesma origem para frontend, cookie e API.
  • Requer acesso à configuração do servidor atual.

Cloudflare Worker + Named Tunnel

Uma route Cloudflare captura gamberine.com.br/gamb-rhid* e encaminha ao backend por um hostname de origem protegido por Tunnel.

  • Útil quando o site raiz não pode ser alterado.
  • Pode ser provisionado por API e infraestrutura como código.
  • Exige token Cloudflare e monitoramento de uma camada adicional.
GitHub Pages não é opção para esta aplicação: ele não executa o backend Node, não mantém SQLite persistente e não protege o token RHiD em cookie HttpOnly.

03

Contratar ou aprovar a infraestrutura de produção

Manual

Escolher provedor, plano, região, cobrança e limites de recursos.

Ajustar o plano do GitHub e proteger a branch main

Manual

Habilitar branch protection/ruleset, impedir force push e exigir CI verde. Definir a alternativa de aprovação caso o plano não ofereça reviewer de deploy para repositório privado.

Criar tokens e chaves com privilégio mínimo

Manual Sensível

Criar Cloudflare API Token, chave SSH de deploy, acesso ao backup e token somente-leitura do GHCR quando necessário.

Cadastrar segredos nos destinos corretos

Manual Sensível

GitHub Environment, secret manager do provedor ou arquivo de ambiente protegido no servidor. Nenhum valor secreto deve entrar no repositório.

Definir e cadastrar usuários no Cloudflare Access

Manual

Confirmar os usuários autorizados e testar o método de autenticação.

Aprovar política de retenção e aviso de privacidade

Manual

A decisão sobre dados pessoais, localização e prazo de retenção precisa de validação do responsável pelo tratamento.

Executar homologação humana no RHiD

Manual

Validar login, consulta, GPS e comportamento visual com uma sessão real. Não registrar ponto oficial durante a homologação.

Aprovar a primeira promoção para produção

Manual

Confirmar versão, backup, rollback, smoke tests e janela de publicação antes de habilitar tráfego e marcação oficial.

Participar do teste de restauração e incidente

Manual recorrente

Validar mensalmente uma restauração e semestralmente o fluxo de incidente, contatos e comunicação.

O que pode ser automatizado após os acessos

Estes itens podem ser implementados no repositório e executados de forma repetível pela esteira.

04

Adaptar toda a aplicação para /gamb-rhid

Automatizável

Ajustar base Vite/PWA, assets, service worker, API, cookies, redirects e testes. Hoje o projeto usa /gamb_rhid/ e chamadas em /api; ambos precisam ser migrados.

Aplicar segurança fail-closed

Automatizável

Marcação oficial desabilitada por padrão, validação de sessão no servidor, idempotência, cabeçalhos, origem confiável, rate limit e logs sem segredos.

Container Docker endurecido

Automatizável

Build multi-stage, usuário sem root, healthcheck, filesystem somente leitura, volume exclusivo para dados e limites de recursos.

Migrations e backups consistentes do SQLite

Automatizável

Schema versionado, WAL, integrity check, backup online, criptografia, retenção e restauração automatizada em ambiente isolado.

CI completa para cada pull request

Automatizável

Auditoria, lint, typecheck, testes, cobertura, integração simulada, build, scanner de segredo, scanner de imagem e E2E sem envio oficial.

Versionamento e release

Automatizável

SemVer, changelog, tag assinada, GitHub Release, SBOM, proveniência e imagem GHCR com versão, SHA e digest imutável.

Deploy automático em homologação

Automatizável

Publicar a imagem aprovada, executar migration, readiness, smoke tests, E2E e relatório de implantação.

Promoção controlada para produção

Automatizável após aprovação

Promover exatamente o digest homologado, criar backup, implantar, validar saúde e registrar GitHub Deployment.

Rollback automático

Automatizável

Retornar ao digest anterior quando readiness ou smoke test falhar, sem promover artefato diferente do que foi testado.

Configuração Cloudflare por código

Automatizável

Worker route ou Tunnel, políticas, hostname de origem e validações podem ser versionados após o API Token ser criado manualmente.

Monitoramento e alertas

Automatizável

Disponibilidade, expiração TLS, uso de disco, falhas do SQLite, backups, erros 5xx, deploys e reconciliações não confirmadas.

Documentação operacional gerada junto com a release

Automatizável

Runbook, matriz de segredos, inventário de versões, procedimento de rollback e evidências de testes atualizados pela esteira.

Sequência de implementação

Ordem proposta para evitar configurar produção antes de existirem testes, backup e rollback.

06

Fase 0 · Coleta e decisões

Saída: hospedagem, roteamento, acessos, responsáveis, retenção e objetivos operacionais definidos.

Fase 1 · Preparação do código

Saída: caminho /gamb-rhid, segurança fail-closed, migrations, idempotência, readiness e encerramento gracioso.

Fase 2 · Container e dados

Saída: imagem reproduzível, volume persistente, backup online e restore validado.

Fase 3 · CI, versão e registro

Saída: pull requests protegidos, imagem GHCR assinada, SBOM, changelog e release por SemVer.

Fase 4 · Homologação

Saída: deploy automático, envio oficial bloqueado, testes E2E e validação humana concluída.

Fase 5 · Produção

Saída: publicação por digest, backup prévio, smoke tests, monitoramento e rollback comprovado.

Fase 6 · Operação contínua

Saída: alertas, renovação de segredos, testes de restore, atualização de dependências e revisão periódica de acesso.
